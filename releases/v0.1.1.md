# Agentic Foundry v0.1.1

Source-release packaging correction for the initial Agentic Foundry repository baseline. The pinned `2026-11-20-r5` runtime payload and the fresh-machine / Claude → OMP deployment workflows are unchanged.

## What changed

- Source archive creation preserves the committed Git LFS pointers instead of expanding them into the large runtime payload.
- The publisher checks the source archive's content boundary before attaching it to the release.
- Recommended versioned checkout, deployment-state, tag, and standalone-tar examples now use `v0.1.1`.

The source asset is intended for reviewing and maintaining the integration. Obtain the actual LFS objects before disconnected deployment, or export the complete standalone tar from a hydrated checkout.

## Why this is a new patch version

The `v0.1.0` publication attempt completed verification of every remote payload file, then failed during source packaging. `git archive` applied LFS expansion and the intended source-only archive exceeded 2 GiB. GitHub release publication did not complete.

The original `v0.1.0` tag and its historical release notes remain unchanged. This correction is delivered under a new tag rather than replacing the original version. Successful remote payload verification establishes artifact integrity; it does not establish installation or task acceptance on the receiving machine.

## Same complete payload

The repository still supplies the declared r5 runtime dependencies, selected upstream source snapshots, licenses, documentation, and provenance through content-addressed Git LFS objects. No tool, image, package, model-route configuration, or platform profile is upgraded by this packaging patch.

The stack retains Paperclip/PostgreSQL coordination; OMP, Claude Code, Codex, OpenCode and optional Herdr; native tools and reviewed skill/hook integration; Worktrunk; RTK OSS; Zoekt/Ctags; seven language services; Inspect AI and native benchmarking; Playwright/Chromium; Trivy; and Go.

Private source preference, native package ownership, configuration preservation, and the manual Claude-to-OMP phase boundary remain in force. No new monitoring, telemetry, backup, or replacement memory platform is introduced.

## Platform and acceptance boundaries

The complete supplied fallback and evaluation/browser profile target Debian 13 on x86-64/glibc. Other Linux distributions, ARM64 and musl need matching qualified private profiles or payload builds.

Actual native upgrades, Docker worker execution, private-model protocol/tool behavior, project delivery, and preservation of the receiving machine's configuration remain target acceptance checks. The builder checked Chromium bytes, dependencies, version and relocation; its environment blocked real UI interaction, so the sandbox-enabled target browser gate remains required.

This patch adds no claim of new target qualification. The payload does not include model weights, arbitrary future project dependencies, every optional upstream build graph/history, the proprietary Claude Code implementation source, or the optional Trivy Java class index.

## Get started

Follow the repository README, `docs/QUICKSTART.md`, and `docs/PAYLOADS.md`. Select the `v0.1.1` tag, retrieve and verify its real LFS objects before disconnecting, and provide the actual private site configuration with credentials kept outside Git.

For a single transferable kit, hydrate the clean tagged checkout and use `build-tools/export-release.py --ref v0.1.1`. The exporter verifies source and payload identities, includes one copy of the complete payload, and emits the tar checksum and per-member validation report.
